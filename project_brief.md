# Project Brief: Social Media Interaction API

## 1. Overview
The **Social Media Interaction API** is a high-performance Spring Boot microservice designed to handle real-time social media interactions. Acting as an API gateway, the service processes requests related to user registration, bot creation, post publishing, commenting, and liking.

A major focus of this system is **high concurrency, scalability, and strict guardrails**. To achieve this, the architecture relies heavily on **PostgreSQL** for relational data persistence and **Redis** for state management, rate-limiting, and batched background processing.

---

## 2. Architecture & Tech Stack
The application follows a standard layered Spring Boot architecture (`Controller` -> `Service` -> `Repository` -> `Database`).

### Tech Stack
*   **Core Framework**: Java 17, Spring Boot 3.5.14
*   **Primary Database**: PostgreSQL (accessed via Spring Data JPA)
*   **Cache & State Store**: Redis (accessed via Spring Data Redis & `StringRedisTemplate`)
*   **Deployment**: Docker (configured via `docker-compose`)

### Architectural Decisions
*   **Statelessness**: The API is completely stateless, making it highly horizontally scalable.
*   **Concurrency Control**: Race conditions during high traffic (e.g., thousands of simultaneous likes) are prevented using Redis's atomic operations.
*   **Guardrails & Rate Limiting**: Redis is utilized to implement horizontal and vertical caps on user/bot actions, ensuring system stability.

---

## 3. Data Models (Entities)
The domain is modeled using JPA entities that map directly to the PostgreSQL schema:
*   **`User`**: Represents human users on the platform.
*   **`Bot`**: Represents automated agents that can interact with content.
*   **`Post`**: The core content generated by users.
*   **`Comment`**: User or Bot responses tied to a specific `Post`.
*   **`Author`**: A generalized entity to link actions back to the creator.

---

## 4. API Endpoints
The RESTful endpoints are split across multiple controllers:

### User & Bot Management (`UserBotController`)
*   `POST /user`: Registers a new human user.
*   `POST /bot`: Registers a new bot entity.

### Content Creation (`FunctionController`)
*   `POST /api/posts`: Creates and publishes a new post.

### Interactions (`LikeController` & `CommentController`)
*   `POST /api/posts/{postId}/comments`: Adds a comment to the specified post.
*   `POST /api/posts/{postId}/like`: Submits a like for the specified post.

---

## 5. Background Processes & Redis Integrations
One of the most complex elements of the application is its background notification sweeping mechanism. 

### The Notification Sweeper (`NotificationSweeper.java`)
To prevent the end-user from being spammed with notifications (especially when bots rapidly interact with posts), the system queues pending push notifications in Redis under the key pattern: `user:{userId}:pending_notifs`.

A scheduled cron job (`@Scheduled(fixedRate = 300000)`) runs every 5 minutes and performs the following sequence:
1.  **Scans Redis**: Finds all `pending_notifs` list keys for all users.
2.  **Summarizes**: Retrieves the size of the pending list for a user.
3.  **Formats Output**: Pops the first interaction (e.g., a Bot name) and summarizes the rest. For instance: *"Bot_A and [5] others interacted with your posts"*.
4.  **Clears State**: Safely deletes the Redis list key for that user, ensuring the batch is processed exactly once.

### Cache Configuration (`CacheConfig.java`)
The application implements `@EnableCaching` with a TTL (Time-To-Live) of 30 minutes for cached entries to optimize frequent read operations without overwhelming the PostgreSQL database.

---

## 6. Conclusion
This architecture successfully decouples high-throughput writes (like rate-limiting and notification queueing via Redis) from permanent data persistence (via PostgreSQL). The result is a robust, responsive system capable of handling viral posts and heavy bot traffic without failing.
